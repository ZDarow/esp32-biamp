# Разделение направлений и владение путями

Документ описыет, как четыре направления развиваются параллельно, не
конфликтуя. Ветки живут в этом же репозитории и выкладываются на GitHub: у
каждой свой workflow, а `main` собирает дерево целиком.

## Зачем это нужно

Раньше всё лежало в одной ветке `main` и в одном файле `.github/workflows/ci.yml`.
Из этого следовало три практических проблемы:

- правка прошивки и правка приложения в одном рабочем дереве мешали друг другу
  ещё до коммита — незакоммиченные изменения блокировали переключение ветки;
- `ci.yml` содержал три независимые задачи, поэтому любая правка прошивки и
  любая правка приложения меняли один и тот же файл;
- `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md` менялись с обеих
  сторон и служили гарантированным источником конфликтов при слиянии.

Разнесение по долгоживущим веткам проблему не решает: файлы остаются общими,
и конфликт просто переезжает из рабочего дерева в момент слияния. Поэтому
разделение построено на владении путями — одном владельце на файл.

## Четыре направления

| Направление | Ветка | Свои пути |
|---|---|---|
| Прошивка ESP32 | `firmware-dev` | `firmware/**`, кроме `capture/` и `tools/capture-analyze.py`; `firmware/protocol/status-contract.md` (контракт протокола); `SECURITY.md`; `.github/workflows/ci-firmware.yml` |
| Приложение Android | `android-dev` | `android-app/**`, `.github/workflows/ci-android.yml` |
| Веб-панель и клиент для ПК | `pc-client-dev` | `pc-client/**`, `.github/workflows/ci-pc-client.yml` |
| Проверки и измерения | `verify-dev` | `firmware/capture/**`, `firmware/tools/capture-analyze.py`, `.github/workflows/ci-verify.yml` |

Направление проверок выделено из прошивки, потому что это другая работа:
прошивка пишет формулы DSP, проверки меряют результат и пишут методику аудита.
Сниффер `firmware/capture/` — это отдельная прошивка ESP32-S3 для захвата
цифрового выхода Master, и её правки идут вместе с анализатором, а не вместе
с аудиотрактом.

**Владение путями.** Контракт протокола `firmware/protocol/status-contract.md` —
источник истины формата команд — принадлежит прошивке и правится только
согласованно со всеми тремя реализациями; он явно закреплён за `firmware` во
всех трёх копиях матрицы (хук, CODEOWNERS, этот файл).

**Проверки не пишут протокол.** Они читают его, чтобы разбирать захваты, но
не могут менять ни `firmware/ESP32_BiAmp/`, ни лимиты `safeCmdVal()`. Это
осознанное ограничение: если разметку захвата сможет поправить тот, кто не
владеет прошивкой, методика аудита перестанет быть независимой.

**Ветка `pc-client-dev` сохранена** под направлением веб-панели: переименование
ветки обрывает её историю и ссылки, а `webapp.py` всё равно делит пакет
`biamp` с `protocol.py` и `transport.py`. Разделить CLI и веб-панель по путям
нельзя без выноса общего кода в отдельный пакет — это отдельная задача.

## Общие файлы

Их вправе править любое направление, но они — единственный источник
конфликтов, поэтому правьте их отдельным маленьким коммитом:

`README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `LICENSE`,
`.gitignore`, `.gitattributes`, `.editorconfig`, `docs/**`, `.githooks/**`,
`.github/workflows/ci-hygiene.yml`, `.github/workflows/release.yml`.

Матрица объявлена в трёх местах и должна меняться во всех трёх сразу:

- `.githooks/pre-commit` — работает локально, без сети;
- `.github/CODEOWNERS` — заработает на GitHub после первого пуша;
- этот файл — объясняет причину.

Три копии расходятся незаметно: удалённый из хука путь начинает молча
пропускать правку из чужой ветки. Сверка запускается вручную и в CI:

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\check-owners.ps1
```

### Порядок правил решает всё

`firmware/capture/` принадлежит проверкам, а `firmware/**` — прошивке, поэтому
в матрице есть два правила, покрывающих один файл. Побеждает более узкое, и
способ, которым это определяется, различается:

- **в `.githooks/pre-commit`** (`sh`) выигрывает **первое** совпавшее
  правило — узкие шаблоны стоят выше широких;
- **в `.github/CODEOWNERS`** выигрывает **последнее** совпавшее — узкие
  правила стоят ниже широких;
- **в `tools/check-owners.ps1`** сверка моделирует обе семантики — первое
  совпадение для хука и последнее для CODEOWNERS — и сравнивает результат
  с самым узким правилом, независимо от порядка. Так она ловит не только
  расхождения владельцев, но и перестановку строк: правило, выигравшее не
  по ширине, а по позиции, — это баг.

Позиция catch-all тоже часть матрицы: в CODEOWNERS `*` стоит первым
(при последнем совпадении catch-all в конце файла перекрыл бы все правила
выше), в хуке — последним (при первом совпадении он сделал бы конкретные
правила недостижимыми). Свёрка проверяет и это.

Перестановка правил в любом из трёх файлов тихо ломает разделение, поэтому
сверка матрицы обязана быть в CI.

## Активация локальной проверки

Один раз в каждом клоне:

```bash
git config core.hooksPath .githooks
```

После этого `git commit` из ветки `firmware/*` откажется принимать файлы
приложения. Обход — `git commit --no-verify` или `SKIP_PATH_OWNER=1 git commit`.
Пользуйтесь обходом осознанно: он ровно возвращает конфликт, который схема
задумана снять.

## Рабочий цикл

```bash
git checkout firmware-dev
git switch -c firmware/volume-ramp      # короткая ветка под задачу
# ... правки ...
git add firmware/                       # только свои пути
git commit -m "..."
git checkout firmware-dev && git merge --ff-only firmware/volume-ramp
git checkout main && git merge --ff-only firmware-dev
```

**История `main` должна быть линейной.** У ветки включена
`required_linear_history`, и push с merge-коммитом помечается нарушением:
«This branch must not contain merge commits». Пуш при этом проходит — правило
не применяется к администраторам (`enforce_admins: false`), так что нарушение
проходит молча, и история `main` заросла merge-коммитами. Поэтому merge-коммит
в `main` не создавайте: направление перед слиянием переписывает историю через
`rebase` (следующий раздел), а `main` двигается только быстрым перемотом
`--ff-only`.

## Синхронизация направлений

Направления не должны расходиться надолго, иначе `main` придётся сливать в
столкновении:

```bash
git checkout firmware-dev
git fetch origin
git rebase origin/main     # подтянуть чужие изменения, конфликт = чужой файл
git push --force-with-lease origin firmware-dev
git checkout main && git merge --ff-only firmware-dev
git push origin main
```

Перезапись истории ветки направления безопасна: её читает только владелец
направления, а `main` с неё не переписывается никогда. `--force-with-lease`
вместо `--force` — чтобы не затереть чужую работу, если ветку уже кто-то
продвинул.

Ожидаемо, что `git rebase main` в ветке прошивки даст конфликт в
`README.md`, если приложение меняло его же. Это единственное место, где
разрешение вручную — и именно поэтому общие файлы стоит править отдельным
коммитом.

## Один worktree на направление

Направлений четыре, а рабочее дерево одно — правки разных направлений
смешиваются в одном каталоге и блокируют переключение ветки. Дерево на
направление:

```bash
git worktree add ../androiddev-work android-dev
git worktree add ../webdev-work   pc-client-dev
git worktree add ../verifydev-work verify-dev
```

Внутри дерева направления собирается только его часть: `android-dev` не
содержит скетча прошивки, `verify-dev` не содержит Gradle-проекта. Сборка
всего дерева целиком остаётся обязанностью `main`.

## Железо — узкое место направления проверок

Математику DSP ловят host-тесты `firmware/tests/` — обычный компилятор, без
платы:

```bash
cd firmware/tests && make test-host
```

Но замер АЧХ, задержки и клиппинга требует ESP32, усилителей и колонок в
комнате. **Два прогона одновременно невозможны:** один и тот же Master, один
комплект акустики. Порядок работы с железом всегда такой:

1. замерить эталон на текущей прошивке;
2. прошить новую версию;
3. перемерить и сравнить с эталоном.

Поэтому направление проверок параллельно с прошивкой только до шага 2, и
правку прошивки нельзя совмещать с прогоном замеров на том же устройстве.
Громкость при замерах — не выше 6%, подробности в `AGENTS.md` §4.

## Проверенное поведение

Схема проверена на шести сценариях:

| Сценарий | Результат |
|---|---|
| Правка своего файла из `firmware/*` | коммит проходит |
| Правка чужого файла из `firmware/*` | отказ с кодом 1 и списком |
| Правка `firmware/capture/AUDIT.md` из `verify/*` | коммит проходит |
| Правка `firmware/ESP32_BiAmp/*.ino` из `verify/*` | отказ |
| Правка своего и общего файла | проходит с предупреждением об общем |
| Новый файл вне матрицы | отказ: «никем не описан» |
| Перестановка правил в CODEOWNERS (узкое выше широкого) | сверка краснеет: последнее совпадение меняет владельца |
| Перестановка правил в хуке (узкое ниже широкого) | сверка краснеет: первое совпадение меняет владельца |
| Две ветки, каждая правит свой файл, слияние в `main` | без конфликтов, стратегия `ort` |
| Две ветки, обе правят `README.md`, слияние | конфликт только в `README.md` |
| Merge-коммит в `main` | пуш проходит с пометкой нарушения `required_linear_history` |

Обе последние строки — проверено на практике. Общий файл остаётся
единственным источником конфликтов, и конфликт локализован в нём, а не
расползается по направлениям. Пометка о merge-коммите неочевидна: пуш
проходит, потому что правило не распространяется на администраторов, — и
нарушение остаётся незамеченным, пока история не станет нелинейной.

## Чего схема не решает

Файлы разведены физически, а связь между ними — смысловая. Протокол
описан в `firmware/protocol/status-contract.md` (контракт — источник
истины формата) и реализован трижды: в
`firmware/ESP32_BiAmp/ESP32_BiAmp.ino`, в
`android-app/app/src/main/java/com/kilo/biampcontrol/bt/Protocol.kt` и в
`pc-client/biamp/protocol.py`. Новую команду в протоколе нужно заводить во
все четырёх местах — контроль владения путями этого не проверит. Проверяют
тесты: `Protocol.kt` — `StatusParserTest`, `protocol.py` — `test_protocol.py`.

Второе ограничение — физическое: замеры требуют единственного устройства.
Параллелизм направлений ограничен одним Master, а не числом веток.
