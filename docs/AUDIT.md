## 3. Незавершённая функциональность

### 3.1 Перестановка Л/П реализована без интерфейса — ОТКРЫТО

Lint сообщает о пяти неиспользуемых ресурсах
(`android-app/app/src/main/res/values/strings.xml`):

```
строка 18  R.string.action_connect
строка 19  R.string.action_disconnect
строка 102 R.string.lr_swap
строка 103 R.string.lr_swap_caption
строка 104 R.string.lr_switch
```

Проверено: в коде приложения ни одного упоминания. При этом:

- контракт v35 описывает команду `swap:` с диапазоном `0..1`
  (`firmware/protocol/status-contract.md:91`)
- контракт описывает поле статуса `SWP: N` как «новое в v35»
  (`firmware/protocol/status-contract.md:51`)
- парсер читает это поле (`bt/Protocol.kt:237`) и модель содержит
  поле `swapped` (`bt/Protocol.kt:85`)

То есть прошивка командует, протокол её разбирает, а управлять ей
нечем. Строки переведены на оба языка и готовы к использованию —
нужен элемент интерфейса. Удалять их не следует: это заготовка
недоделанной функции, а не мусор.

## 4. Логика и границы значений

### 4.1 Границы зашиты в UI вместо `Limits` — ОТКРЫТО

`android-app/app/src/main/java/com/kilo/biampcontrol/ui/DspTab.kt`

```kotlin
112:  range = 200f..1000f,   // частота кроссовера
121:  range = 20f..80f,      // сабсоник
```

В том же файле для эквалайзера используется константа
(`DspTab.kt:271`):

```kotlin
valueRange = Limits.EQ_MIN..Limits.EQ_MAX
```

Смешение двух подходов. `safeCmdVal()` в прошивке — источник истины,
`Limits` — его зеркало в клиенте. Если граница кроссовера изменится
на устройстве, ползунок продолжит показывать старое значение, а
пользователь — отправлять число, которое прошивка отбросит.

Именно этот класс дефекта закрывает контрактный тест
`LimitsContractTest`, но на текущих константах `Limits` тест проходит:
проблема в том, что UI их не использует.

### 4.2 Закрытый пробел по контракту — ИСПРАВЛЕНО

Раздел 4 `firmware/protocol/status-contract.md` — единая таблица
диапазонов для всех клиентов — не проверялся ни одним тестом ни в одном
клиенте.

Добавлено 28 тестов (`3b51566`): 13 в Android читают таблицу из файла
контракта, 15 в клиенте для ПК проверяют константы и поведение
построителей. `tvol:` защищён от возврата диапазона 0..100.

## 5. Зависимости и воспроизводимость

### 5.1 Граф Android: конфликтов нет

`debugRuntimeClasspath` и `debugAndroidTestRuntimeClasspath` разрешаются
без конфликтов версий:

```
kotlin-stdlib:2.0.21
compose-bom:2025.09.00 → ui 1.9.1, material3 1.3.2, material-icons 1.7.8
lifecycle-viewmodel-compose:2.8.7 → 2.9.0   (транзитивное повышение)
kotlinx-coroutines-android:1.9.0
```

Зависимости `compose.*` без версий — управляются BOM, схема верная.

### 5.2 Material3 1.4.0 недостижим без смены тулчейна — РИСК

`UI-PLAN.md` и задача №1 объявляют целью Material3 1.4.0. Фактически
BOM 2025.09.00 приносит 1.3.2. Версия 1.4.0 лежит в BOM 2026.09.00,
но переход тянет за собой смену AGP и Kotlin.

Ограничение зафиксировано в коде: lint 31.7.3 из AGP 8.7.3 разобран
против Kotlin Analysis API K1 и роняет `lintAnalyzeDebug` на K2.
Список падающих детекторов — `K2_CRASHING_LINT_IDS` в
`android-app/app/build.gradle.kts`.

Обновлять BOM без смены AGP и Kotlin нельзя: получится неверная
версия вместо рабочей сборки.

### 5.3 Линт молча отключает часть проверок — РИСК

Предупреждение `ObsoleteLintCustomCheck`: проверки из реестра
`androidx.compose.ui.lint.UiIssueRegistry` ссылаются на недействительные
API и будут пропущены. Lint выдаёт меньше гарантий, чем кажется, и не
сообщает об этом как об ошибке.

### 5.4 Локальная сборка прошивки не воспроизводима — ОТКРЫТО

`ci-firmware.yml` фиксирует все версии по тегам и хешам коммитов —
это образцово. Оба хеша сверены с фактическими и совпадают.

`firmware/tools/build.ps1` и `firmware/tools/common.ps1` не содержат
ни одной проверки библиотек: локальная сборка берёт `master` обеих
GitHub-библиотек. Расхождение объяснимо только в одну сторону:
«у меня работает, а в CI нет».

### 5.5 pyserial задана диапазоном — ОТКРЫТО

`pc-client/requirements.txt:3`

```
pyserial>=3.5,<4
```

Единственная внешняя зависимость продакшн-кода не зафиксирована. Тот же
класс дефекта, что описан в комментарии самого `pc-client/pyproject.toml`
как уже найденный ранее.

### 5.6 Локальные версии инструментов расходятся с CI — ОТКРЫТО

| Пакет | Локально | В CI |
|---|---|---|
| mypy | 2.3.1 | 2.4.0 |
| ruff | 0.16.6 | 0.16.10 |
| types-pyserial | 3.5 | 3.5.0.20260712 |

`requirements-dev.txt` фиксирует версии ради воспроизводимости, и в CI
фиксация есть. Локальный прогон всё равно может считать другое — это
произошло при проверке: локальный `mypy` дал ошибки отсутствия стабов
`pyserial`, которых в CI нет.

## 6. Типизация

### 6.1 Python: 95 тестов вне mypy — ОТКРЫТО

`pc-client/pyproject.toml:56` — `files = ["biamp"]`.

Проверяются 7 файлов продакшн-кода под `strict = true`. Тесты не
проверяются на типы вообще: контракт между тестом и кодом типами не
охраняется, расхождение сигнатуры обнаружится в рантайме.

В тестах при этом ноль `Any`, аннотации есть — включение, скорее всего,
пройдёт без правок кода.

### 6.2 Python: ошибки mypy на этой машине — не дефект проекта

Локальный прогон даёт:

```
biamp/transport.py:21:  error: Library stubs not installed for "serial.tools"
biamp/transport.py:144: error: Library stubs not installed for "serial"
```

Причина проверена: `python3` в этой оболочке указывает на виртуальное
окружение постороннего проекта (`~/.profile:34` добавляет
`$HOME/pygpsclient/bin` в `PATH`). `types-pyserial` установлен в
системных `dist-packages`, а окружение имеет
`include-system-site-packages = false` и стабов не видит.

В чистом виртуальном окружении с системным интерпретатором 95 тестов
проходят, стабы на месте. **Конфигурация проекта и CI корректны**,
расходится локальная машина.

### 6.3 Kotlin: типо-антипаттернов нет

Проверено: ноль `!!`, ноль `runBlocking`, ноль `GlobalScope`.
Компиляция чистая.

## 8. Структура репозитория

### 8.1 Конфликт имён Gradle-проекта — ОТКРЫТО

`android-app/settings.gradle.kts:15` — `rootProject.name = "BiAmpControl"`
при каталоге `android-app`.

оба Gradle-проекта, и имя `BiAmpControl-android-app` совпадает, что даёт
`Duplicate root element` и падение импорта.

Проверено: при удалении второго корня импорт встаёт правильно.

### 8.2 Монолит прошивки — ОТКРЫТО, низкий приоритет

`firmware/ESP32_BiAmp/ESP32_BiAmp.ino` — 1 596 строк, 73 глобальные
переменные, 40 вхождений `String(`, 6 `delay()`.

Не является дефектом: работает, покрыто самотестом кольцевого буфера
и диагностическими счётчиками. Затрудняет ревью — любая правка даёт
diff по всему файлу.

Требует проверки перед любым разбиением: `Ring selftest: PASS` и
нулевые `RingDrops`/`BadSamples`/`Underrun` на устройстве.
