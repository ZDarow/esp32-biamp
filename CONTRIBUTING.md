## С чего начать

1. Откройте [Issues](https://github.com/ZDarow/esp32-biamp/issues)
   и проверьте, не обсуждается ли тема уже.
2. Для крупных изменений сначала создайте issue с описанием
   идеи — так обсудим подход до реализации.
3. Для мелких правок сразу переходите к pull request.
4. Определите, к какому направлению относится правка
   (см. [распределение задач](#распределение-задач)), и
   работайте в ветке этого направления.

## Окружение

### Прошивка

| Компонент | Версия |
|---|---|
| [arduino-cli](https://arduino.github.io/arduino-cli/latest/installation/) | свежая |
| ESP32 core | `esp32:esp32` 3.x |
| PowerShell | 5.1 или новее (`powershell` или `pwsh`) |

```bash
arduino-cli core update-index
arduino-cli core install esp32:esp32
arduino-cli lib install "Adafruit GFX Library" "Adafruit SSD1306"

# audio-tools и ESP32-A2DP отсутствуют в реестре Arduino —
# публикуются только на GitHub, поэтому ставятся вручную:
git clone --depth 1 https://github.com/pschatzmann/arduino-audio-tools.git \
  "$(arduino-cli config get directories.user)/libraries/audio-tools"
git clone --depth 1 https://github.com/pschatzmann/ESP32-A2DP.git \
  "$(arduino-cli config get directories.user)/libraries/ESP32-A2DP"
```

### Приложение

| Компонент | Версия |
|---|---|
| JDK | 17 |
| Android SDK | platform 35, build-tools 35.0.0 |
| Gradle | 8.9 (через wrapper) |

Создайте `android-app/local.properties`:

```properties
sdk.dir=C:\\Android\\Sdk
```

### Клиент для ПК

| Компонент | Версия |
|---|---|
| Python | 3.10–3.14 |
| pyserial | `>=3.5,<4` — единственная внешняя зависимость |

```powershell
cd pc-client

```

### Проверки и измерения

Сниффер собирается ESP-IDF (`idf.py -C firmware/capture`),
анализатор — Python 3.14 с numpy. Математика DSP проверяется
без платы: `cd firmware/tests && make test-host`.

## Проверка перед коммитом

Оба компонента обязаны собираться. CI делает то же самое, но
локальная проверка быстрее и экономит время на pull request.
Полный список команд по направлениям —
[docs/TESTING.md](docs/TESTING.md).

### Прошивка

```powershell
pwsh -File .\firmware\tools\build.ps1
```

### Приложение

```bash
cd android-app
.\gradlew.bat assembleDebug
.\gradlew.bat testDebugUnitTest
.\gradlew.bat lintDebug
```

### Клиент для ПК

```powershell
cd pc-client
python -m unittest discover -s tests -t .
```

### Матрица владения

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\check-owners.ps1
```

Скомпилированный APK обязан работать на устройстве: подключиться
к устройству, прочитать `status`, изменить параметр и увидеть
отклик.

## Параллельная работа

### Стратегия ветвления

Четыре долгоживущие ветки направлений + линейный `main`:

```
main ────────────────────────────────────────────────▶
  ▲              ▲               ▲              ▲
  │ ff-only      │ ff-only       │ ff-only      │ ff-only
firmware-dev  android-dev    pc-client-dev  verify-dev
  ▲              ▲               ▲              ▲
  │              │               │              │
firmware/…    android-app/…   pc-client/…    firmware/capture/…
```

- **`main` собирает дерево целиком** и двигается только
  быстрым перемотом (`--ff-only`). Merge-коммит в `main`
  создавать нельзя: история обязана быть линейной.
- **Ветка направления** перед слиянием переписывает историю
  через `rebase` на `origin/main`.
- **Ветка задачи** — короткоживущая, от ветки направления:
  `firmware/volume-ramp`, `ui/phase2-adaptive`, `verify/sweep-axis`.
  Имя — `kebab-case` на английском.

```bash
git checkout firmware-dev
git switch -c firmware/volume-ramp
# ... правки ...
git add firmware/
git commit -m "Исправить переполнение кольцевого буфера"
git checkout firmware-dev && git merge --ff-only firmware/volume-ramp
git checkout main && git merge --ff-only firmware-dev
```

### Распределение задач

Каждая задача принадлежит ровно одному направлению —
владельцу затрагиваемых путей. Задача, которая трогает файлы
двух направлений, разбивается на две согласованные задачи.

| Направление | Ветка | Свои пути | Примеры задач |
|---|---|---|---|
| Прошивка ESP32 | `firmware-dev` | `firmware/**` (кроме `capture/` и `tools/capture-analyze.py`), `SECURITY.md`, `ci-firmware.yml` | DSP, ресемплинг, NVS, OTA, протокол |
| Приложение Android | `android-dev` | `android-app/**`, `ci-android.yml` | UI, парсер `status`, SPP-клиент |
| Веб-панель и клиент ПК | `pc-client-dev` | `pc-client/**`, `ci-pc-client.yml` | CLI, веб-панель, профили |
| Проверки и измерения | `verify-dev` | `firmware/capture/**`, `firmware/tools/capture-analyze.py`, `ci-verify.yml` | сниффер, анализатор, методика аудита |

**Проверки не пишут протокол.** Они читают его, чтобы разбирать
захваты, но не могут менять ни `firmware/ESP32_BiAmp/`, ни
лимиты `safeCmdVal()`. Это осознанное ограничение: если разметку
захвата сможет поправить тот, кто не владеет прошивкой,
методика аудита перестанет быть независимой.

**Парная задача** (пример — кубическая громкость, issue #6):
правка `vol_z` в прошивке + `StatusParser` в приложении +
`VolumeTab`. Порядок обязателен: сначала прошивка, потом
приложение, иначе интерфейс будет врать. Такие задачи
согласуются между владельцами направлений до начала работы.

**Общие файлы** (`README.md`, `AGENTS.md`, `CONTRIBUTING.md`,
`docs/**`, `.githooks/**`, `tools/**`) правит любое направление
— отдельным маленьким коммитом, чтобы конфликт при слиянии
был маленьким.

**Железо — узкое место.** Замеры требуют единственного ESP32,
усилителей и колонок. Два прогона одновременно невозможны.
Порядок: замерить эталон → прошить → перемерить. Направление
проверок параллельно прошивке только до шага «прошить».

### Владение путями

Матрица объявлена в трёх местах и должна меняться во всех
трёх сразу:

- `.githooks/pre-commit` — работает локально, без сети;
- `.github/CODEOWNERS` — заработает на GitHub после первого
  пуша;
- `docs/BRANCHING.md` — объясняет причину.

Сверка:

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\check-owners.ps1
```

Активация хука — один раз в каждом клоне:

```bash
git config core.hooksPath .githooks
```

После этого `git commit` из ветки `firmware/*` откажется
принимать файлы приложения. Обход — `git commit --no-verify`
или `SKIP_PATH_OWNER=1 git commit`. Пользуйтесь обходом
осознанно: он ровно возвращает конфликт, который схема
задумана снять.

**Порядок правил решает всё.** `firmware/capture/` принадлежит
проверкам, а `firmware/**` — прошивке, поэтому в матрице два
правила покрывают один файл:

- в `.githooks/pre-commit` (`sh`) выигрывает **первое**
  совпавшее правило — узкие шаблоны стоят выше широких;
- в `.github/CODEOWNERS` выигрывает **последнее** совпавшее —
  узкие правила стоят ниже широких;
- в `tools/check-owners.ps1` выигрывает самое длинное
  совпавшее правило, независимо от порядка.

Перестановка правил в любом из трёх файлов тихо ломает
разделение, поэтому сверка матрицы обязана быть в CI.

### Разрешение конфликтов

Конфликт возможен только в общих файлах — в файлах одного
направления конфликт невозможен по построению (один владелец).

1. **Не сливайте чужую работу в свою ветку направления.**
   Подтягивайте `main` через `rebase`:

   ```bash
   git checkout firmware-dev
   git fetch origin
   git rebase origin/main     # конфликт = чужой файл
   git push --force-with-lease origin firmware-dev
   git checkout main && git merge --ff-only firmware-dev
   ```

2. **Конфликт в `README.md`** (или другом общем файле) —
   единственное место, где разрешение вручную. Правило:
   сохранить правки обеих сторон, не выбрасывать чужое.
   Если правки перекрываются по смыслу — согласуйте с автором
   чужого коммита.

3. **`--force-with-lease` вместо `--force`** — чтобы не затереть
   чужую работу, если ветку уже кто-то продвинул. Перезапись
   истории ветки направления безопасна: её читает только
   владелец направления, а `main` с неё не переписывается
   никогда.

4. **Не решайте конфликт, затрагивающий чужие пути, молча.**
   Если `rebase` поднял конфликт в файле другого направления —
   остановитесь и согласуйте: это признак, что задача была
   разбита неправильно.

### Код-ревью

Правила ревью для всех направлений:

1. **Собственные пути.** Правка из ветки `firmware/*` должна
   затрагивать только `firmware/**` (кроме `capture/` и
   `tools/capture-analyze.py`) и общие файлы. Хук это
   проверяет локально, CI — на сервере.
2. **Документация в том же коммите.** Изменился протокол,
   формат `status`, лимит значения — обновлены все три
   реализации и документация. Команда, которой нет в прошивке,
   устройство молча проигнорирует.
3. **Диапазоны совпадают с `safeCmdVal()`.** Лимит в UI не
   выходит за пределы прошивки. Меняете потолок — правьте
   оба места (пример: `MAX_DELAY_SAMPLES = 220` при
   `DELAY_BUF_SIZE = 256`).
4. **Счётчики здоровья.** После любой правки тракта в логе:
   `Ring selftest: PASS`, `RingDrops: 0`, `SelfTestErr: 0`,
   `Underrun Z1=0 Z2=0`, `Clips 0/0/0/0`. `bad > 0` —
   публикация запрещена.
5. **Тесты.** Юнит-тесты для чистой логики (`StatusParserTest`,
   `test_protocol.py`, `firmware/tests/`), инструментированные
   — для поведения на Android-рантайме.
6. **Стиль.** Kotlin: 4 пробела, 120 символов; скетч: 2
   пробела, 100 символов; комментарии на русском; имена —
   английский `snake_case`/`camelCase`. Правила закреплены в
   `.editorconfig` и `.gitattributes`.
7. **Один коммит — одно логическое изменение.** Рефакторинг
   не смешивается с новой функциональностью.

## Чек-листы слияния

Полные чек-листы — [docs/MERGE-CHECKLIST.md](docs/MERGE-CHECKLIST.md).
Краткая выжимка перед каждым слиянием в `main`:

- [ ] История линейна: `git log --merges main` пуст для новых
      коммитов
- [ ] Сборка обоих компонентов проходит
- [ ] Тесты зелёные (юнит + инструментированные)
- [ ] Счётчики здоровья нулевые на устройстве

      протокол)
- [ ] Матрица владения согласована: `tools/check-owners.ps1`
- [ ] Общие файлы правились отдельным коммитом

## Правила оформления коммитов

Коммиты на русском языке, в повелительном наклонении:

```
Исправить переполнение кольцевого буфера при переносе
Добавить логарифмическую шкалу частот для chhp
Обновить документацию под прошивку v35
```

Содержимое коммита — одно логическое изменение. Не смешивайте
рефакторинг с новой функциональностью: их удобнее ревьюить
раздельно.

## Что важно знать о проекте

### Источник истины — прошивка

Приложение подстраивается под прошивку, а не наоборот.
Прежде чем изменить формат команды или парсер в `android-app`,
сверьтесь с `firmware/ESP32_BiAmp/ESP32_BiAmp.ino` и
[контрактом v35.1](firmware/protocol/status-contract.md).

**Команда, которой нет в прошивке, будет молча проигнорирована
устройством.** Это уже случалось: кнопка отправляла `meta`,
которой в прошивке не существует.

### Протокол описан трижды

`firmware/ESP32_BiAmp/ESP32_BiAmp.ino`,
`android-app/.../bt/Protocol.kt` и `pc-client/biamp/protocol.py`.
Новую команду в протоколе нужно заводить во всех трёх местах —
контроль владения путями этого не проверит. Проверяют тесты:
`Protocol.kt` — `StatusParserTest`, `protocol.py` —
`test_protocol.py`.

### Аудиотракт критичен к памяти

Кольцевой буфер — обычный линейный массив, а не кольцо на
указателях. Любое копирование через физический конец
переполняет буфер и портит соседние переменные. Симптомы:
треск при нулевых `RingDrops` и `Underrun`.

После любых изменений в тракте обязателен самотест при загрузке:

```
Ring selftest: PASS frames=10752/10752 bad=0 drops=0
```

`bad > 0` означает порчу данных — публиковать такую сборку
нельзя.

### Размеры и стили

- Kotlin: отступ 4 пробела, строки до 120 символов
- Скетч: отступ 2 пробела, строки до 100 символов
- Комментарии на русском языке
- Имена переменных и функций — английский, `snake_case` и
  `camelCase`
- Названия веток — `kebab-case` на английском: `fix/delay-limit`

Правила закреплены в `.editorconfig` и `.gitattributes`.

## Запрещено

- ❌ Коммитить файлы сборки, логи и захваты Bluetooth
- ❌ Коммитить `local.properties` — он содержит локальные пути

- ❌ Менять протокол SPP без обновления документации в том же
  коммите
- ❌ Создавать merge-коммит в `main`
- ❌ Поднимать громкость тест-сигнала выше 6 % ради проверки

## Pull request

1. Создайте ветку от ветки своего направления с понятным
   именем.
2. Внесите изменения, запустите обе сборки.
3. Обновите документацию, если изменился протокол или поведение.
4. Опишите в PR, что изменилось и **как это проверено** — на
   каком устройстве, с какими счётчиками.
5. Откройте pull request в `main`.

### Хорошее описание PR

```
Исправить переполнение кольцевого буфера при переносе

ringPush копировал данные одним memcpy через физический конец
ring_buf. При RING_FRAMES=4096 и SELFTEST_CHUNK=896 запись
стартовала с индекса 8190 при размере массива 8192 элементов —
выход за границу ~3580 байт.

Проверка на COM15, прошивка v35:
- Ring selftest: PASS frames=10752/10752 bad=0 drops=0
- 30 с внутреннего теста: RingDrops: 0, SelfTestErr: 0,
  Underrun 0/0
- WR max 8364 мс (было 19414)
```
